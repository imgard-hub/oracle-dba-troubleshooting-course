What Really Happened (The Real Incident)

A junior DBA was on call and encountered two separate crises on the same day:

🔴 Issue 1: Archive Logs Filling FRA

The Fast Recovery Area (FRA) filled up to 50GB and crashed the database. Investigation revealed that the RMAN backup job had silently been failing since March 3rd because the database VM shuts down at 5 PM — but the backup job was scheduled to run at 00:20 (midnight). No backup = no deletion = disk fills.

🔴 Issue 2: Missing Control Files (VM Clone)

A cloned VM had its database pointed to control files that still lived on the source VM. Oracle couldn't start — it looked for files that didn't exist on the new server. This required locating the control files, copying them over safely, and validating startup.

MODULE 01

Finding Errors & Alert Logs

When something goes wrong with Oracle, your first job is to find the evidence. The alert log is the most important file you'll ever read as a DBA. It records every database startup, shutdown, error, and significant event in chronological order.

📍 Where to Find the Alert Log

⚠️
Rule #1: Always check the alert log FIRST before assuming anything. It will tell you what actually happened.

Method 1: Using ADR (Recommended — Oracle 11g+)

SQL*Plus
-- From SQL*Plus, find the alert log location
SELECT value FROM v$diag_info WHERE name = 'Diag Trace';

-- Or check your ADR base
SHOW PARAMETER diagnostic_dest;

Method 2: Standard Path Pattern

Linux / OS Shell
# Oracle 11g and above (ADR structure)
$ORACLE_BASE/diag/rdbms/<db_name>/<SID>/trace/alert_<SID>.log

# Example (replace ORCL with your SID)
/u01/app/oracle/diag/rdbms/orcl/ORCL/trace/alert_ORCL.log

# If you don't know ORACLE_BASE, check environment
echo $ORACLE_BASE
echo $ORACLE_SID

Method 3: Find It If You Don't Know the Path

Linux Shell
# Search the filesystem for the alert log
find / -name "alert_*.log" 2>/dev/null

# Or search common Oracle paths
find /u01 /u02 /opt/oracle -name "alert_*.log" 2>/dev/null

📖 How to Read the Alert Log

The alert log can be thousands of lines long. Here's how to work with it efficiently:

Reading the Alert Log — Key Commands
# View the LAST 100 lines (most recent events)
tail -100 alert_ORCL.log

# Watch it live (like watching TV — see new events as they happen)
tail -f alert_ORCL.log

# Search for ALL Oracle errors
grep -i "ORA-" alert_ORCL.log

# Search for a specific error
grep "ORA-00257" alert_ORCL.log

# Show errors with surrounding context (5 lines before and after)
grep -B5 -A5 "ORA-00257" alert_ORCL.log

# Search for recent errors (filter by date)
grep -A5 "2024-03-04" alert_ORCL.log | grep -i "ORA-"

# Count how many times an error appears
grep -c "ORA-00257" alert_ORCL.log

🔑 Understanding What You're Reading

What You SeeWhat It MeansWhat To Do
ORA-00257Archiver error — archive log destination is full or inaccessibleCheck FRA space, backup archive logs
ORA-01034ORACLE not available — instance is down or failed to startCheck what error came just BEFORE this
ORA-00210Cannot open the specified control fileCheck if control files exist at listed paths
ORA-00202Control file path specified in parameter fileShows you exactly which file Oracle is looking for
ORA-01078Failure in processing system parametersCheck spfile/pfile for syntax or missing parameters
LRM-00109Could not open parameter fileLocate and verify pfile/spfile exists
Termination of instanceOracle gave up trying to start — NOT the real error, just the resultScroll UP to find the actual cause
🎯
Critical Rule: When you see "Termination of instance" — that is NOT the problem. That is Oracle telling you "I tried and failed." Always scroll UP in the log to find the real error one or two lines above it.

📁 Other Important Log Locations

Other Log Locations
# Background process trace files (detailed crash info)
$ORACLE_BASE/diag/rdbms/<dbname>/<SID>/trace/

# RMAN logs (if your script uses tee/logging)
# Look for $LOG_FILE variable in your RMAN script
grep -i "LOG_FILE\|log_file" /path/to/rman_script.sh

# Cron execution logs (did the scheduled job actually run?)
grep CRON /var/log/cron

# Syslog (system-level errors)
tail -50 /var/log/messages
tail -50 /var/log/syslog    # Debian/Ubuntu

# Oracle audit files
$ORACLE_BASE/admin/<SID>/adump/
🧠 Key Concept: ADRCI Tool

Oracle provides a tool called ADRCI (ADR Command Interpreter) to work with diagnostic data without navigating file paths manually.

ADRCI Tool
# Launch ADRCI
adrci

# Inside ADRCI — show all homes
show homes

# Set your home
set home diag/rdbms/orcl/ORCL

# Show recent problems
show problem

# Show incidents (more detail)
show incident

# Exit
exit
MODULE 02

Instance Startup & Shutdown Sequence

Understanding the startup sequence is essential for troubleshooting. When a database fails to start, the stage at which it fails tells you exactly what kind of problem you have.

🚀 Oracle Startup Sequence — 4 Stages

Stage 0 → Stage 1
SHUTDOWN → NOMOUNT
Oracle reads the parameter file (spfile or pfile), allocates the SGA (System Global Area) in memory, and starts background processes (PMON, SMON, DBWR, LGWR, CKPT, ARCn, etc.).
Command
STARTUP NOMOUNT;
⚠️
Failure here means: Missing or corrupt spfile/pfile, SGA too large for memory, insufficient OS privileges, or missing ORACLE_SID
Stage 1 → Stage 2
NOMOUNT → MOUNT
Oracle reads the control files. The control file paths are defined in the parameter file. Oracle reads the control files to learn about the database structure — datafiles, redo logs, and DB name.
Command
ALTER DATABASE MOUNT;
-- Or from shutdown:
STARTUP MOUNT;
🔴
Failure here means: Control files are MISSING, at WRONG PATH, or CORRUPT. This is exactly what happened in the VM clone incident (ORA-00210, ORA-00202).
Stage 2 → Stage 3
MOUNT → OPEN
Oracle opens the datafiles and redo log files. It verifies that the SCN (System Change Number) in the control file matches the datafiles — confirming a consistent database state.
Command
ALTER DATABASE OPEN;
-- Or from shutdown (full sequence):
STARTUP;
⚠️
Failure here means: Missing datafiles, missing redo logs, SCN mismatch (need recovery), or the database needs media recovery after crash.
Stage 3
OPEN — Database Running
Users can connect. Oracle applies any redo from online redo logs if the previous shutdown was not clean (instance recovery). The database is fully operational.
✅
Database is open. Verify: SELECT STATUS FROM V$INSTANCE;

🛑 Oracle Shutdown Modes

CommandWaits for Users?Waits for Transactions?Checkpoints?When to Use
SHUTDOWN NORMALYesYesYesPlanned, patient maintenance (users can finish work)
SHUTDOWN TRANSACTIONALNo new connectionsYesYesPlanned shutdown, finish open transactions only
SHUTDOWN IMMEDIATENo — kicks users offRolls back activeYes✅ Standard planned shutdown — use this most often
SHUTDOWN ABORTNoNo — killed mid-flightNo⚠️ Emergency only — next startup needs instance recovery
⚠️
Never use SHUTDOWN ABORT casually. It's like pulling the power cord from a running PC. The next startup will perform automatic instance recovery, which can take time. Always prefer SHUTDOWN IMMEDIATE for planned work.

🔍 Quick Diagnostic Commands by Stage

Diagnostics by Stage
-- Check what stage the database is at
SELECT STATUS FROM V$INSTANCE;
-- Returns: STARTED (nomount), MOUNTED, OPEN

-- Check all background processes are running
SELECT NAME, DESCRIPTION FROM V$BGPROCESS
WHERE PADDR != '00';

-- Check SGA allocation
SHOW SGA;

-- Verify control file status
SELECT NAME, STATUS FROM V$CONTROLFILE;

-- Verify datafile status
SELECT FILE#, NAME, STATUS FROM V$DATAFILE;
MODULE 03

Understanding "Termination of Oracle Instance"

"Termination of Oracle instance" = Oracle tried to start, something went wrong, so it shut itself down immediately. It is NOT the problem — it is Oracle's response to the problem.

Think of it like a car engine: the engine turns over → a sensor detects a critical failure → the system shuts down to prevent damage. The warning light isn't the engine problem — it's the signal that something failed before or during startup.

🔴 What Happens During a Failed Startup

Example: What You Might See in the Alert Log
-- REAL EXAMPLE: What a failed startup looks like

Tue Mar 05 00:20:14 2024
Starting ORACLE instance (normal) (OS id: 12345)
...
ORA-01078: failure in processing system parameters
LRM-00109: could not open parameter file
             '/u01/app/oracle/product/19c/dbs/initORCL.ora'
...
Termination of instance ORCL (pid 12345)
🎯
How to read this: Oracle couldn't find the parameter file (LRM-00109). That's the real problem. Because of that, startup failed. Because startup failed, Oracle terminated the instance. The termination is the last line — work backwards from there.

🔥 Common Root Causes of Instance Termination

📄 Missing / Wrong Parameter File
  • Oracle looks for spfile<SID>.ora first
  • Then init<SID>.ora (pfile)
  • Located in $ORACLE_HOME/dbs/
  • Check: ls -la $ORACLE_HOME/dbs/
💾 SGA Too Large
  • sga_max_size exceeds available OS memory
  • Check: free -m on OS
  • Fix: Reduce SGA parameters in pfile
  • Error: ORA-27102 (out of memory)
📁 Missing Control Files
  • Paths in control_files parameter don't exist
  • Common after VM clone or file move
  • Error: ORA-00210, ORA-00202
  • Check: show parameter control_files
🔐 Permission Issues
  • Oracle files not owned by oracle:oinstall
  • Common after manual file copies
  • Fix: chown oracle:oinstall <file>
  • Error: ORA-27040 or ORA-27047

🛠️ Your Immediate Response Plan

  1. Stay Calm — Read the Error Above Termination
    Open the alert log. The termination line is at the bottom. The REAL error is 1–5 lines above it. That's what you're solving.
  2. Identify the ORA- Error Code
    Write it down. ORA-01078? Parameter file issue. ORA-00210? Control file issue. Each code tells you exactly where to look next.
  3. Try to Reach NOMOUNT First
    Run STARTUP NOMOUNT; — if this works, at least the parameter file is fine and memory allocated. Move to the next stage.
  4. Fix the Root Cause
    Based on the error: restore the file, fix paths, correct permissions, or reduce memory parameters.
  5. Attempt Full Startup Again
    Run STARTUP; and monitor the alert log in real-time with tail -f alert_ORCL.log
MODULE 04

Archive Log Destination Full

The archive log situation in this real incident had three layers: (1) disk appeared fine but FRA was logically full, (2) the backup job was configured correctly but never ran because the DB was down at midnight, (3) the deletion policy blocked cleanup because logs weren't backed up first.

📚 Key Concepts to Understand First

🗂️ What Are Archive Logs?

In ARCHIVELOG mode, Oracle saves a copy of every filled redo log to a destination (FRA or custom path). These are used for point-in-time recovery. They accumulate constantly and must be managed.

📦 What Is the FRA?

Fast Recovery Area — a disk location Oracle manages for backups, archive logs, and control file copies. It has a defined size limit. When it reaches capacity, Oracle stops archiving, which halts the database.

🚨
Key insight: Oracle does NOT care about OS free space. Even if you have 100GB free on the disk, if the FRA is logically "full" (at its configured limit), Oracle will stop. The FRA limit is a logical boundary you set, not a physical one.

🔍 Step-by-Step Diagnosis

STEP 1 — Check FRA Usage
-- Check FRA configured space and current usage
SELECT
  NAME,
  SPACE_LIMIT/1024/1024/1024 "GB_LIMIT",
  SPACE_USED/1024/1024/1024 "GB_USED",
  SPACE_RECLAIMABLE/1024/1024/1024 "GB_RECLAIMABLE",
  NUMBER_OF_FILES
FROM V$RECOVERY_FILE_DEST;

-- Check OS-level disk space too
-- (run from Linux shell, not SQL*Plus)
df -h
STEP 2 — Check RMAN Policies
-- Connect to RMAN
rman target /

-- Check retention policy (how long backups are kept)
SHOW RETENTION POLICY;

-- Check archive log deletion policy (when Oracle is ALLOWED to delete)
SHOW ARCHIVELOG DELETION POLICY;

-- Check when backups last ran
LIST BACKUP OF ARCHIVELOG ALL;
LIST BACKUP SUMMARY;
STEP 3 — Check Current Archive Log Status
-- From SQL*Plus
ARCHIVE LOG LIST;

-- Check archiving errors in alert log
grep -i "ORA-00257\|archiv" alert_ORCL.log | tail -20

🚨 Understanding the Deletion Policy (This Is Critical)

Deletion Policy SettingMeaningRisk
NONEOracle never automatically deletes archive logsHIGH — fills forever
BACKED UP 1 TIMES TO DISKOracle only deletes after log is backed up at least onceMEDIUM — safe but requires backup job to run
APPLIED ON STANDBYOnly for Data Guard — delete after applied to standbyData Guard only
💡
The real incident used "BACKED UP 1 TIMES TO DISK." This is a safe policy — but only if backups are actually running. When the backup job failed silently, logs piled up because Oracle refused to delete un-backed-up logs. The policy was doing its job correctly — the backup job was the problem.

🛠️ Fix: Immediate Recovery Steps

RMAN — Backup Then Delete (Safe Method)
-- Connect to RMAN
rman target /

-- Method 1: Backup first, then delete separately (most controlled)
BACKUP ARCHIVELOG ALL;
DELETE ARCHIVELOG ALL COMPLETED BEFORE 'SYSDATE-2';

-- Method 2: Backup AND delete in one command (efficient, urgent use)
BACKUP ARCHIVELOG ALL DELETE INPUT;

-- Method 3: Delete only what's obsolete per retention policy
REPORT OBSOLETE;
DELETE OBSOLETE;

-- After cleanup, verify FRA recovered space
-- (from SQL*Plus)
SELECT SPACE_USED/1024/1024/1024 "GB_USED"
FROM V$RECOVERY_FILE_DEST;
⛔
NEVER manually delete archive logs from the OS with rm. Oracle won't know they were removed. RMAN metadata will show them as existing. Always use RMAN to delete archive logs so the catalog stays consistent.

🔧 Fix: Resize the FRA (Temporary Mitigation)

SQL*Plus — Resize FRA
-- Increase FRA size (this is what the student did: 50G → 70G)
ALTER SYSTEM SET DB_RECOVERY_FILE_DEST_SIZE = 70G SCOPE=BOTH;

-- Check new limit is active
SHOW PARAMETER DB_RECOVERY_FILE_DEST_SIZE;
🎓 Teaching Point: Temporary vs Permanent Fix

Increasing the FRA size buys time — it is NOT the solution. The real fix is:

  • Get backups running successfully again
  • Ensure the backup job runs while the database is UP
  • Set up monitoring/alerting so FRA issues are caught early
  • Verify deletion policy is appropriate and functioning

💥 Why the Backup Job Failed: Schedule Mismatch

The root cause of this entire incident was a schedule mismatch:

🕔 Database Shutdown

Every day at 5:00 PM

This is a dev environment. The VM is shut down at end of business each day to save resources.

🕛 RMAN Backup Script

Scheduled at 00:20 (midnight)

The script ran every night — but the database was not running. Result: ORA-01034 every time.

What the RMAN Log Showed (Root Cause Evidence)
RMAN connected to target database (not started)

ORA-01034: ORACLE not available
ORA-27101: shared memory realm does not exist
-- Translation: The database was DOWN when backup tried to run
-- Every night since March 03: same failure, same silence

✅ Permanent Fix: Reschedule the Backup Job

Linux Cron — Fix the Schedule
# Edit the crontab
crontab -e

# OLD (broken): runs at midnight when DB is down
20 0 * * * /path/to/rman_backup.sh >> /path/to/backup.log 2>&1

# NEW (fixed): runs at 4:00 PM, before 5 PM shutdown
0 16 * * * /path/to/rman_backup.sh >> /path/to/backup.log 2>&1

# OR: runs at 8:15 AM after DB starts in the morning
15 8 * * * /path/to/rman_backup.sh >> /path/to/backup.log 2>&1

# Verify current crontab
crontab -l

🔍 Verifying Your RMAN Script Is Working

Script Health Check
# Find the LOG_FILE variable in your RMAN script
grep -i "LOG_FILE\|log_file" /path/to/rman_backup.sh

# If LOG_FILE is undefined, test it
echo $LOG_FILE
# If this returns blank → variable not set → no log output

# Verify Oracle environment variables are set in cron script
grep -i "ORACLE_HOME\|ORACLE_SID\|PATH" /path/to/rman_backup.sh

# Check cron executed the job
grep CRON /var/log/cron | grep rman_backup

# Run the script manually to test
/path/to/rman_backup.sh

# Check RMAN backup history
rman target /
LIST BACKUP SUMMARY;
MODULE 05

Missing Control Files (ORA-00210 / ORA-00202)

Control files are the most critical file type in Oracle. They contain the map of the entire database — where every datafile and redo log lives, the database name, the current SCN, and backup history. Oracle cannot progress past NOMOUNT without them.

🧠 What Happened: VM Clone Scenario

Alert Log — What You'd See
ORA-00210: cannot open the specified control file
ORA-00202: control file: '/u01/oradata/ORCL/control01.ctl'
ORA-27037: unable to obtain file status
Linux-x86_64 Error: 2: No such file or directory
...
Termination of instance ORCL
💡
ORA-00202 is actually helpful — it tells you exactly which file Oracle can't find. The path listed there is your starting point.

🔍 Diagnose: Is It a Wrong Path or a Missing File?

  1. Get to NOMOUNT first
    STARTUP NOMOUNT; — If this works, the parameter file is fine. The failure is at the MOUNT stage (control files).
  2. Check what paths Oracle expects
    SHOW PARAMETER control_files; — Write down ALL paths listed. These are what Oracle is looking for.
  3. Check if files exist at those paths (OS level)
    For each path returned above, run ls -l /path/to/control01.ctl in Linux shell.
  4. Search for control files anywhere on the system
    find / -name "*.ctl" 2>/dev/null — This finds any control files, even if in wrong locations.

🚀 Fix Options — Choosing the Right Approach

Are control files missing on the new VM?
├── YES → Do they exist on the source VM / old server?
│ ├── YES → Option A: Copy control files from source
│ └── NO → Does an RMAN backup exist?
│ ├── YES → Option B: RMAN RESTORE CONTROLFILE
│ └── NO → Do datafiles and redo logs exist?
│ ├── YES → Option C: CREATE CONTROLFILE
│ └── NO → Database is unrecoverable without a valid backup
└── NO → Paths are just wrong
└── Option D: Fix control_files parameter in pfile

Option A: Copy Control Files from Source VM

Safe Copy Procedure
==== ON THE SOURCE (OLD) VM ====
# Step 1: Shut down the source database cleanly FIRST
sqlplus / as sysdba
SHUTDOWN IMMEDIATE;

# Step 2: Find control files
find /u01 /u02 -name "*.ctl" 2>/dev/null

==== FROM YOUR WORKSTATION / NEW VM ====
# Step 3: Create destination directories on new VM
mkdir -p /u01/oradata/ORCL
mkdir -p /u02/fra/ORCL

# Step 4: Copy control files via SCP
scp oracle@oldvm:/u01/oradata/ORCL/control01.ctl \
    oracle@newvm:/u01/oradata/ORCL/
scp oracle@oldvm:/u02/fra/ORCL/control02.ctl \
    oracle@newvm:/u02/fra/ORCL/

==== ON THE NEW VM ====
# Step 5: Fix ownership and permissions
chown oracle:oinstall /u01/oradata/ORCL/control01.ctl
chown oracle:oinstall /u02/fra/ORCL/control02.ctl
chmod 640 /u01/oradata/ORCL/control01.ctl
chmod 640 /u02/fra/ORCL/control02.ctl

# Step 6: Attempt startup mount
sqlplus / as sysdba
STARTUP MOUNT;

# Step 7: If mounted successfully, open the database
ALTER DATABASE OPEN;

# Step 8: Validate
SELECT STATUS FROM V$INSTANCE;
SELECT NAME, STATUS FROM V$CONTROLFILE;

Option B: Restore from RMAN Backup

RMAN Restore Control File
-- Connect to RMAN at NOMOUNT
sqlplus / as sysdba
STARTUP NOMOUNT;
exit

rman target /

-- Restore from autobackup (if available)
RESTORE CONTROLFILE FROM AUTOBACKUP;

-- Or restore from a specific backup piece
RESTORE CONTROLFILE FROM '/path/to/backup/ctl_backup.bkp';

-- Mount after restore
ALTER DATABASE MOUNT;
RECOVER DATABASE;
ALTER DATABASE OPEN RESETLOGS;

Option C: Recreate Control File (Last Resort)

CREATE CONTROLFILE — Use only if no backup exists
-- First: find a trace backup if Oracle created one previously
find $ORACLE_BASE -name "*.trc" | xargs grep -l "CREATE CONTROLFILE" 2>/dev/null

-- Basic CREATE CONTROLFILE template
-- (You must list ALL datafiles and redo logs accurately)
STARTUP NOMOUNT;

CREATE CONTROLFILE REUSE DATABASE "ORCL" RESETLOGS
  MAXLOGFILES 16
  MAXLOGMEMBERS 3
  MAXDATAFILES 100
  MAXINSTANCES 8
LOGFILE
  GROUP 1 '/u01/oradata/ORCL/redo01.log',
  GROUP 2 '/u01/oradata/ORCL/redo02.log',
  GROUP 3 '/u01/oradata/ORCL/redo03.log'
DATAFILE
  '/u01/oradata/ORCL/system01.dbf',
  '/u01/oradata/ORCL/sysaux01.dbf',
  '/u01/oradata/ORCL/users01.dbf',
  '/u01/oradata/ORCL/undotbs01.dbf'
CHARACTER SET AL32UTF8;

ALTER DATABASE OPEN RESETLOGS;
ALTER TABLESPACE TEMP ADD TEMPFILE '/u01/oradata/ORCL/temp01.dbf' SIZE 500M;
⚠️
Option C is advanced and risky. Getting any datafile path wrong can corrupt recovery. Always prefer Options A or B. If you must use this, verify every file path on the OS before running the command.

Option D: Fix Wrong Path in Parameter File

Fix Paths in PFILE / SPFILE
-- The files EXIST but Oracle is looking in the wrong directory

-- Step 1: Export current spfile to pfile (editable text)
-- (If you can reach NOMOUNT)
CREATE PFILE='/tmp/init_temp.ora' FROM SPFILE;

-- Step 2: Edit the pfile (in Linux shell)
vi /tmp/init_temp.ora
-- Find the control_files line and update paths to correct location

-- Step 3: Startup using the corrected pfile
STARTUP PFILE='/tmp/init_temp.ora';

-- Step 4: If it works, recreate spfile from corrected pfile
CREATE SPFILE FROM PFILE='/tmp/init_temp.ora';

-- Step 5: Bounce database to use new spfile
SHUTDOWN IMMEDIATE;
STARTUP;
MODULE 06

RMAN Backup Failures & Verification

RMAN (Recovery Manager) is Oracle's built-in backup and recovery tool. A junior DBA must know how to verify that backups are actually working — not just configured.

🔑 Core Rule: Configuration ≠ Working

Having a backup script scheduled does not mean backups are happening. Your job is to verify they actually ran and succeeded — every time. Automation without validation is just delayed failure.

Essential RMAN Commands Every Junior DBA Needs

RMAN Reference Commands
-- Connect to RMAN
rman target /

========= CHECKING CONFIGURATION =========
SHOW ALL;                          -- All RMAN settings
SHOW RETENTION POLICY;             -- How long backups are kept
SHOW ARCHIVELOG DELETION POLICY;   -- When archive logs can be deleted
SHOW DEFAULT DEVICE TYPE;          -- Where backups go (disk/tape)

========= VERIFYING BACKUP HISTORY =========
LIST BACKUP SUMMARY;               -- Overview of all backups
LIST BACKUP OF ARCHIVELOG ALL;     -- Archive log backups only
LIST BACKUP OF DATABASE;           -- Full database backups
LIST ARCHIVELOG ALL;               -- All archive logs Oracle knows about

========= CHECKING FOR PROBLEMS =========
REPORT OBSOLETE;                   -- Backups outside retention window
REPORT NEED BACKUP;                -- Files that need to be backed up
CROSSCHECK BACKUP;                 -- Verify backup files still exist on disk
CROSSCHECK ARCHIVELOG ALL;         -- Verify archive logs still exist

========= RUNNING BACKUPS =========
BACKUP ARCHIVELOG ALL;             -- Backup all archive logs
BACKUP ARCHIVELOG ALL DELETE INPUT;-- Backup AND delete logs after
BACKUP DATABASE;                   -- Full database backup
BACKUP DATABASE PLUS ARCHIVELOG;   -- Database + archive logs together

========= CLEANUP =========
DELETE OBSOLETE;                   -- Delete backups outside retention
DELETE EXPIRED BACKUP;             -- Delete catalog entries for missing files
DELETE ARCHIVELOG ALL COMPLETED BEFORE 'SYSDATE-2'; -- Delete logs older than 2 days

🔧 Diagnosing a Failed Backup Script

RMAN Script Health Check Procedure
# 1. Open the script and find key variables
cat /path/to/rman_backup.sh

# 2. Check for required Oracle environment variables
grep -E "ORACLE_HOME|ORACLE_SID|PATH|BACKUP_DIR|LOG_FILE" /path/to/rman_backup.sh

# 3. Test if variables are set in the current shell
echo $ORACLE_HOME
echo $ORACLE_SID
echo $LOG_FILE
echo $BACKUP_DIR

# 4. Check cron actually executed the job
grep CRON /var/log/cron | grep -i backup | tail -20

# 5. Find and read the log file
# (once you know LOG_FILE path from the script)
tail -50 /path/to/backup.log
grep -i "ORA-\|RMAN-\|error\|failed" /path/to/backup.log

# 6. Run the script manually to test
bash /path/to/rman_backup.sh

# 7. Verify backup appeared in RMAN catalog
rman target /
LIST BACKUP SUMMARY;

📋 RMAN Script Requirements Checklist

Every RMAN script run from cron must have these elements or it will fail silently:

  • ORACLE_HOME — Full path to Oracle software (e.g., /u01/app/oracle/product/19c/dbhome_1)
  • ORACLE_SID — Database instance name (e.g., ORCL)
  • PATH — Must include $ORACLE_HOME/bin so rman command is found
  • BACKUP_DIR — Destination path for backup pieces (must exist and be writable)
  • LOG_FILE — Where script output is written (directory must exist)
  • Database is UP — Job schedule must align with database availability window
  • Error checking — Script should exit with error code on RMAN failure
  • Alerting — Failure should trigger email/notification to DBA team

Hands-On Labs

These labs simulate the exact incidents from this course. Complete them on a test Oracle instance (never production). Each lab builds a skill you'll use in real incidents.

Lab 1 — Navigate to the Alert Log & Find Errors
Beginner ~20 min
Objective: Locate the Oracle alert log, read it, search for errors, and practice the key alert log commands.
  1. Find Your Alert Log Location
    Log into SQL*Plus as sysdba. Run SELECT value FROM v$diag_info WHERE name = 'Diag Trace'; — write down the path returned.
  2. Navigate to the Directory
    Open a Linux shell. cd to the path from step 1. Run ls -la and confirm alert_<SID>.log exists.
  3. View Recent Events
    Run tail -50 alert_<SID>.log. Identify the most recent startup and shutdown events.
  4. Search for ORA Errors
    Run grep "ORA-" alert_<SID>.log. Count how many errors appear. Are any repeating?
  5. Watch Live
    Open a second terminal. In terminal 1, run tail -f alert_<SID>.log. In terminal 2, connect via SQL*Plus and run a simple query. Observe if anything appears in terminal 1.
✅
Success criteria: You can find the alert log, read it, and search for errors without help. You know where to go first when something breaks.
Lab 2 — Simulate & Recover from Archive Log Full
Intermediate ~45 min
Objective: Temporarily reduce FRA size to force the archive full condition, then recover from it using RMAN.
  1. Check Current FRA Size and Usage
    Run: SELECT SPACE_LIMIT/1024/1024/1024 GB_LIMIT, SPACE_USED/1024/1024/1024 GB_USED FROM V$RECOVERY_FILE_DEST; — document baseline values.
  2. Check RMAN Policies
    In RMAN: SHOW RETENTION POLICY; and SHOW ARCHIVELOG DELETION POLICY; — document what you find.
  3. Verify Last Backup Date
    In RMAN: LIST BACKUP OF ARCHIVELOG ALL; — note the most recent backup date.
  4. Simulate the Fix: Backup Archive Logs
    In RMAN: BACKUP ARCHIVELOG ALL; — wait for it to complete successfully.
  5. Clean Up Old Logs
    In RMAN: DELETE ARCHIVELOG ALL COMPLETED BEFORE 'SYSDATE-2'; — confirm deletion.
  6. Verify FRA Space Recovered
    Re-run the V$RECOVERY_FILE_DEST query. Confirm GB_USED decreased.
✅
Success criteria: You backed up archive logs via RMAN and safely deleted old ones. FRA usage decreased. You understand why deleting via RMAN is required, not OS commands.
Lab 3 — Simulate Missing Control File Recovery
Advanced ~60 min
Objective: Copy a control file to a temp location, update the parameter file to point to the wrong path, observe the startup failure, then recover by restoring the control file.
⚠️
Test environment only. Do this only on a non-production database you can afford to break and restore.
  1. Document Current Control File Locations
    SHOW PARAMETER control_files; — write down ALL paths.
  2. Create a Backup Copy of Control File
    In Linux: cp /u01/oradata/ORCL/control01.ctl /tmp/control01.ctl.bak
  3. Simulate Missing File
    Shut down the database with SHUTDOWN IMMEDIATE. Then rename the control file: mv /u01/oradata/ORCL/control01.ctl /tmp/control01_moved.ctl
  4. Try to Start the Database
    Run STARTUP;. Observe the error. Read the alert log to confirm ORA-00210/ORA-00202.
  5. Recover: Restore the File
    mv /tmp/control01_moved.ctl /u01/oradata/ORCL/control01.ctl — Verify permissions with ls -la.
  6. Start Database and Validate
    STARTUP; — Confirm database opens. Check SELECT NAME, STATUS FROM V$CONTROLFILE;
✅
Success criteria: You observed the exact error a missing control file produces, read it in the alert log, and successfully recovered from it.
Lab 4 — Diagnose a "Silent" Cron Backup Failure
Intermediate ~30 min
Objective: Write a simple RMAN backup script, schedule it in cron without proper environment variables (to simulate a broken script), observe the failure, then fix it.
  1. Create a Simple RMAN Test Script
    Write a bash script that runs rman target / @backup.rman without setting ORACLE_HOME or ORACLE_SID. Schedule it in cron to run 2 minutes from now.
  2. Observe the Failure
    Wait 3 minutes. Check grep CRON /var/log/cron to confirm it ran. Check the output log — it should show "rman: command not found" or similar.
  3. Fix the Script
    Add the required environment variable exports at the top of the script: ORACLE_HOME, ORACLE_SID, and updated PATH. Reschedule for 2 minutes from now.
  4. Verify Success
    Wait 3 minutes. Check the log output. Confirm RMAN connected and backup ran successfully. Verify in RMAN with LIST BACKUP SUMMARY;
✅
Success criteria: You understand why cron jobs need explicit environment variables, and you can diagnose and fix a silently failing backup script.

Scenario-Based Simulations

Work through each scenario as if it's a real incident. You receive the alert — what do you do? Walk through each step before looking at the suggested actions.

🚨 SCENARIO 01
Monday 8AM: "The Database Won't Connect"

You arrive at work. A developer calls saying they can't connect to the database. They're getting "ORA-01034: ORACLE not available." You have SSH access to the server.

▶ Show Suggested Approach
Walkthrough
# 1. SSH to the server and check if Oracle process is running
ps -ef | grep -i pmon

# 2. If no PMON process, instance is down. Try to start it
sqlplus / as sysdba
STARTUP;

# 3. If startup fails, read the alert log immediately
tail -100 $ORACLE_BASE/diag/rdbms/<dbname>/<SID>/trace/alert_<SID>.log

# 4. Find the ORA- error ABOVE any "Termination of instance" message
grep -B10 "Termination" alert_<SID>.log | tail -20

# 5. Based on the error code, follow the appropriate resolution path
🚨 SCENARIO 02
FRA at 95% — You Have 30 Minutes Before It Fills

A monitoring alert fires. The FRA is at 95% usage. The database is still up. You need to prevent an outage. You know the last backup ran 3 days ago.

▶ Show Suggested Approach
Emergency Walkthrough
-- Step 1: Verify the situation
SELECT SPACE_USED/SPACE_LIMIT*100 PCT_FULL FROM V$RECOVERY_FILE_DEST;

-- Step 2: Check deletion policy
rman target /
SHOW ARCHIVELOG DELETION POLICY;

-- Step 3: If policy requires backup first, run backup immediately
BACKUP ARCHIVELOG ALL DELETE INPUT;
-- This backs up AND deletes in one shot — good for urgent situations

-- Step 4: Monitor FRA usage dropping
SELECT SPACE_USED/1024/1024/1024 GB_USED FROM V$RECOVERY_FILE_DEST;

-- Step 5: If still tight, temporarily increase FRA size
ALTER SYSTEM SET DB_RECOVERY_FILE_DEST_SIZE = <larger_size>G SCOPE=BOTH;

-- Step 6: Investigate why backup stopped running
🚨 SCENARIO 03
New VM Clone: Database Refuses to Start at MOUNT Stage

A new dev server was just built from a VM clone. The DBA before you left and said "just start the database." You try STARTUP and get ORA-00210. The source VM is still available.

▶ Show Suggested Approach
Recovery Walkthrough
-- Step 1: Confirm you can reach NOMOUNT (parameter file OK)
STARTUP NOMOUNT;

-- Step 2: Find out what paths Oracle is looking for
SHOW PARAMETER control_files;

-- Step 3: Check if those files exist on THIS server
-- (run in Linux shell)
ls -la /path/from/step2

-- Step 4: If missing, search for .ctl files on this server
find / -name "*.ctl" 2>/dev/null

-- Step 5: Since source VM is available, shutdown source DB cleanly
-- On source VM:
SHUTDOWN IMMEDIATE;

-- Step 6: Copy control files from source to new VM
scp oracle@sourcevm:/path/control01.ctl oracle@newvm:/expected/path/

-- Step 7: Fix permissions on new VM
chown oracle:oinstall /path/control01.ctl

-- Step 8: Try startup mount and open
STARTUP MOUNT;
ALTER DATABASE OPEN;
🚨 SCENARIO 04
Backup Job Has Been "Running" But No Backups Exist

You're asked to verify backups are running. You check the crontab — job is there, scheduled daily. But when you check RMAN, LIST BACKUP SUMMARY shows nothing for the last 2 weeks. What happened?

▶ Show Suggested Approach
Diagnosis Walkthrough
# 1. Confirm cron runs the job (not just has it listed)
grep CRON /var/log/cron | grep backup | tail -20

# 2. Find the log file in the script
grep -i "LOG_FILE" /path/to/rman_backup.sh

# 3. Read the log file for errors
tail -100 /path/to/backup.log
grep -i "ORA-\|RMAN-\|error\|failed" /path/to/backup.log

# Most likely you'll see ORA-01034 if DB was down
# Or "rman: command not found" if env variables are missing

# 4. Test the script manually
bash /path/to/rman_backup.sh

# 5. Fix the root cause (environment vars, schedule alignment)
# 6. Run a manual backup to catch up
rman target /
BACKUP ARCHIVELOG ALL;
MODULE 09

Runbooks & SOPs

These are your operational reference documents. Print them, bookmark them, and pull them out during real incidents. They are designed to be followed step-by-step under pressure.

📕
RUNBOOK-01: Database Won't Start
Trigger: STARTUP fails | ORA-01034 | Termination of instance
P1
Owner: DBA Team Est. Time: 15-30 min Last Update: See version control
  1. Read the Alert Log Immediately
    tail -100 $ORACLE_BASE/diag/rdbms/<db>/<SID>/trace/alert_<SID>.log
    Find the ORA- error ABOVE "Termination of instance." Write it down.
  2. Attempt STARTUP NOMOUNT
    STARTUP NOMOUNT;
    If SUCCESS → parameter file is OK, problem is at MOUNT stage (control files)
    If FAIL → problem is with parameter file, memory, or OS
  3. Diagnose Based on ORA- Error Code
    ORA-01078 / LRM-00109 → Missing pfile/spfile → Restore from backup or recreate
    ORA-27102 → SGA too large → Reduce memory params in pfile
    ORA-00210 → Missing control files → Go to RUNBOOK-03
    ORA-00600 → Internal error → Escalate immediately, preserve trace files
  4. Attempt STARTUP MOUNT (if NOMOUNT worked)
    ALTER DATABASE MOUNT;
    If FAIL → Control file issue → See RUNBOOK-03
  5. Open the Database
    ALTER DATABASE OPEN;
    If FAIL → Datafile/redo log issue → Check SELECT FILE#, STATUS FROM V$DATAFILE;
  6. Notify Users and Team
    Send status update to affected teams. Include: what the issue was, what you did, ETA to full resolution.
  7. Document the Incident
    Record the timeline, error codes, root cause, and resolution steps in your incident log.
📗
RUNBOOK-02: Archive Log Destination Full / FRA Full
Trigger: ORA-00257 | DB hangs | FRA > 90%
P1
Owner: DBA Team Est. Time: 20-45 min
  1. Confirm the Problem
    SELECT SPACE_LIMIT/1024/1024/1024 GB_LIMIT, SPACE_USED/1024/1024/1024 GB_USED, (SPACE_USED/SPACE_LIMIT)*100 PCT_USED FROM V$RECOVERY_FILE_DEST;
  2. Check Archive Log Deletion Policy
    In RMAN: SHOW ARCHIVELOG DELETION POLICY; — Is deletion policy set? Does it require backup first?
  3. Check Last Backup Date
    In RMAN: LIST BACKUP OF ARCHIVELOG ALL; — When did the last backup run? Is it recent enough?
  4. EMERGENCY: Run Backup + Delete Now
    In RMAN: BACKUP ARCHIVELOG ALL DELETE INPUT; — This backs up and deletes in one step. Most appropriate under pressure.
  5. Verify Space Recovered
    Re-run step 1 query. Confirm GB_USED decreased significantly. Also check: df -h from Linux shell.
  6. If Still Critical — Temporarily Increase FRA
    ALTER SYSTEM SET DB_RECOVERY_FILE_DEST_SIZE = <new_size>G SCOPE=BOTH; — This buys time but is NOT a permanent fix.
  7. Find Why Backups Stopped
    Check cron: crontab -l. Check cron execution: grep CRON /var/log/cron | grep backup. Find and read the log file from the RMAN script.
  8. Fix the Root Cause & Verify Automation
    Fix schedule, environment variables, or script issues. Run a manual backup to confirm. Verify in RMAN with LIST BACKUP SUMMARY.
📘
RUNBOOK-03: Missing Control Files
Trigger: ORA-00210, ORA-00202 | Startup fails at MOUNT stage
P1
Owner: DBA Team Est. Time: 30-60 min
  1. Confirm Startup Reaches NOMOUNT
    STARTUP NOMOUNT; — If this works, the problem is specifically the control files (not the parameter file or memory).
  2. Get Expected Control File Paths
    SHOW PARAMETER control_files; — Write down ALL paths. These are exactly where Oracle is looking.
  3. Check If Files Exist
    For each path, run ls -la /path/to/control.ctl in Linux. Does the file exist? If yes → permissions/corrupt issue. If no → file is missing.
  4. Search for Control Files on This Server
    find / -name "*.ctl" 2>/dev/null — Are they in a different location? If yes → Fix paths in parameter file.
  5. Choose Recovery Method (Use Decision Tree)
    Source VM available → Copy files (RUNBOOK-03A). RMAN backup exists → Restore (RUNBOOK-03B). No backup or source → Recreate (RUNBOOK-03C — escalate if unsure).
  6. Attempt Startup After Recovery
    STARTUP MOUNT; ALTER DATABASE OPEN; — Monitor alert log for any new errors.
  7. Validate Database Integrity
    SELECT NAME, STATUS FROM V$CONTROLFILE; and SELECT FILE#, STATUS, NAME FROM V$DATAFILE;

Type: Communication Use: Any severity incident

[System/DB name] is experiencing [brief description — e.g., "startup failure" / "FRA near capacity"]. I am currently investigating.

Will update within 30 minutes.

[Your Name]

Status Update (Every 30-60 min until resolved)

Subject: [ENV] Database Issue – Root Cause Identified

Hi [Manager],

Root cause confirmed: [one sentence explanation].

Current status: [what you are doing right now].

Next update: [time].

[Your Name]

Resolution Notice

Subject: [ENV] Database Issue – RESOLVED

The issue has been resolved. [Brief what was done]. Database is now fully operational.

Section A: Concept Questions

Question A-01 · Alert Logs
You see "Termination of Oracle instance" in the alert log. What should you do FIRST?
ARestart the database immediately
BCall your manager
CScroll up in the alert log to find the real ORA- error above this message
DReboot the server
✅ C is correct. "Termination of instance" is Oracle's response to a failure — not the failure itself. The real error is 1–5 lines above it in the alert log. Always read upward from the termination message.
Question A-02 · Startup Sequence
Oracle starts to NOMOUNT successfully, but fails when you try to MOUNT. What does this tell you?
AThe parameter file (spfile/pfile) is corrupted
BThe control files are missing, at the wrong path, or corrupted
CThe SGA is too large for the available memory
DThe redo logs are missing
✅ B is correct. NOMOUNT reads the parameter file and allocates the SGA — if that succeeds, those are fine. MOUNT is where Oracle reads the control files. A failure at MOUNT means control file issues.
Question A-03 · Archive Logs
The FRA is logically full but the OS shows plenty of free disk space. Why is Oracle still blocking archiving?
AOracle has a bug that doesn't check OS disk space
BOracle respects the DB_RECOVERY_FILE_DEST_SIZE limit, not OS free space
CThe archive log format is wrong
DThe RMAN catalog is corrupted
✅ B is correct. The FRA has a configured size limit (DB_RECOVERY_FILE_DEST_SIZE). Oracle manages space within that limit regardless of how much actual disk space is available. To fix this: backup and delete old logs, or increase the FRA size parameter.
Question A-04 · Deletion Policy
SHOW ARCHIVELOG DELETION POLICY returns "BACKED UP 1 TIMES TO DISK" and backups stopped 10 days ago. What happens to archive logs?
AOracle automatically deletes them after 7 days regardless
BNothing — they are kept forever
COracle refuses to delete any archive logs because they haven't been backed up
DRMAN deletes them during the next connection
✅ C is correct. The deletion policy "BACKED UP 1 TIMES TO DISK" means Oracle will ONLY delete archive logs after they have been backed up at least once. If backups stop running, logs accumulate indefinitely — even logs from weeks ago — until backed up.
Question A-05 · Cron & Environment
An RMAN backup script works when run manually as oracle, but fails every night in cron. The most likely reason is:
AThe database is too busy at night
BCron doesn't inherit the oracle user's environment variables (ORACLE_HOME, ORACLE_SID, PATH)
CRMAN doesn't work with cron
DThe backup destination is too small
✅ B is correct. Cron runs in a minimal environment without the user's shell profile loaded. ORACLE_HOME, ORACLE_SID, and PATH must be explicitly exported inside the script itself, or Oracle commands like rman and sqlplus won't be found.

Section B: Short Answer

Question B-01
What command would you run to find the exact path of the Oracle alert log from within SQL*Plus?
SELECT value FROM v$diag_info WHERE name = 'Diag Trace';
This returns the directory path. The alert log filename is alert_<SID>.log in that directory.
Question B-02
What is the difference between RMAN's RETENTION POLICY and ARCHIVELOG DELETION POLICY?
Retention Policy: Defines how long BACKUP PIECES are kept (e.g., "RECOVERY WINDOW OF 7 DAYS" means keep enough backups to recover from any point in the last 7 days).

Archivelog Deletion Policy: Defines WHEN Oracle is allowed to delete archive log files (e.g., "BACKED UP 1 TIMES" means only delete after backed up at least once). These are separate settings that work together.
Question B-03
Why should you NEVER delete Oracle archive logs directly from the OS using the rm command?
Oracle's RMAN catalog maintains a record of every archive log file it knows about. If you delete files directly from the OS, the RMAN catalog still shows them as existing. This causes RMAN to report errors, backups to fail trying to include missing files, and recovery to potentially fail. Always use RMAN DELETE commands so the catalog stays in sync with reality.
Question B-04
A junior DBA runs BACKUP ARCHIVELOG ALL DELETE INPUT — explain what this single command does in two steps.
Step 1: RMAN backs up all archive logs that have not yet been backed up (and any that need to be backed up again per policy).

Step 2: Immediately after backing each log up successfully, RMAN deletes it — both from disk AND updates the catalog. This is the safe, efficient single-command approach for urgent FRA cleanup.
Question B-05
A VM was cloned from a production server. The cloned database fails at MOUNT with ORA-00210. You have no RMAN backup. The source VM is available. List the steps to recover.
1. Run STARTUP NOMOUNT on the new VM to confirm parameter file works
2. Run SHOW PARAMETER control_files to get the expected paths
3. Shut down the SOURCE database cleanly (SHUTDOWN IMMEDIATE)
4. Create destination directories on the new VM if needed (mkdir -p)
5. Copy control files from source VM using scp
6. Fix ownership and permissions on new VM (chown oracle:oinstall; chmod 640)
7. Run STARTUP MOUNT on new VM
8. Run ALTER DATABASE OPEN
9. Validate: SELECT NAME, STATUS FROM V$CONTROLFILE;

Section C: Scenario Questions

Question C-01 · Real World
Your RMAN script runs at midnight, but the DB shuts down at 5 PM. When you check RMAN logs, you see "ORA-01034: ORACLE not available" every night. What is the proper fix?
AReinstall RMAN
BChange the deletion policy to NONE so Oracle auto-deletes
CReschedule the backup job to run before the 5 PM shutdown (e.g., 4 PM)
DKeep the database running 24/7
✅ C is correct. The backup job must run while the database is available. The fix is to reschedule it to run before the shutdown window — 4 PM would work. In cron: change 20 0 * * * to 0 16 * * *. This is the root cause from the real incident in this course.
Question C-02 · Priority Judgment
At 3 PM, the FRA hits 90%. Backups haven't run in 5 days. The database shuts down at 5 PM. What is the correct ORDER of actions?
1. Immediately run BACKUP ARCHIVELOG ALL DELETE INPUT in RMAN — this frees space right now
2. Verify FRA usage decreased and database continues to archive
3. Temporarily increase FRA size if still at risk
4. After the immediate crisis is resolved, investigate WHY backups stopped
5. Fix the backup schedule/script before the 5 PM shutdown
6. Confirm backup runs successfully that day (at new time)
7. Document the incident and send update to team
